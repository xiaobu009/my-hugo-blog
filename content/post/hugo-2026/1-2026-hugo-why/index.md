2026 年，前端技术日新月异，Astro、Gatsby、Next.js 各种框架层出不穷。很多人可能会问：**为什么还要选 Hugo 这个"老家伙"来建站？**

与其给你一份冷冰冰的对比表格，我更想先讲一个真实故事——我是怎么一步步踩坑，最终下定决心换到 Hugo 的。

---

## 1.1 我的踩坑经历：Notion + NotionNext + Vercel

在用 Hugo 之前，我用的是一套当时看起来很优雅的方案：

**Notion 写文章 → NotionNext 框架渲染 → Git 同步 → Vercel 自动部署**

逻辑上这套方案相当吸引人：

- Notion 界面美观，写作体验好，随时随地可以编辑
- NotionNext 基于 Next.js，能把 Notion 页面渲染成博客样式
- Vercel 负责自动化部署，理论上"改完即上线"

听起来完美，实际用下来问题一个接一个。

### 问题一：Vercel 端构建报错，网站直接挂掉

NotionNext 项目本身在持续更新，Vercel 上的 Node.js 环境版本、依赖包版本稍有不兼容，就会在构建时报错。

最让人崩溃的不是报错本身，而是**报错之后网站就挂了**。访客打开你的博客，看到的是一片空白或者 Vercel 的报错页面。我遇到过几次这种情况，每次都要花大量时间去排查是哪个依赖出了问题，有时候根本看不懂报错日志，只能去 NotionNext 的 GitHub Issues 里翻答案。

这直接影响到网站的正常运营——一个技术博客因为框架报错而无法访问，本身就是很讽刺的事情。

### 问题二：想自定义？先去学 Next.js

NotionNext 基于 Next.js 构建，这意味着如果你想对页面样式、布局、功能做任何深度修改，你必须先搞清楚 Next.js 的组件系统、路由机制、`getStaticProps` 是怎么工作的。

对于一个只想专注写内容的博主来说，这个学习成本完全不值当。我只是想改一个侧边栏的样式，却要先理解一整套 React 组件体系。

### 问题三：Notion API 的不确定性

整套方案高度依赖 Notion API 的稳定性。Notion 偶尔的 API 限速、接口变动，都可能导致博客页面无法正常加载。你的内容实际上存在 Notion 的服务器上，而不是你自己完全掌控的地方。

## 1.2 重新审视搭建博客的初衷

折腾了一段时间之后，我问自己：**我搭博客到底想要什么？**

- 本地写好文章，推送后网站自动更新 ✅
- 网站稳定，不会因为框架问题莫名挂掉 ✅
- 能自由修改样式和功能，不需要学一整套 JS 框架 ✅
- 内容完全由自己掌控，不依赖第三方平台 ✅
- 最好免费，不需要买服务器 ✅

带着这几个需求重新看了一遍市面上的方案，最终选择了 **Hugo + Stack 主题 + Cloudflare Pages**。

## 1.3 主流建站方案横向对比

在正式讲 Hugo 之前，先把几个常见方案放在一起比较，帮你找到最适合自己的选择。

### WordPress / Typecho

**适合谁：** 完全不懂技术、需要可视化后台管理内容的用户。

**优点：** 插件生态完整，功能强大，几乎什么需求都能满足。

**缺点：**
- 需要购买服务器和数据库，每年固定成本
- 动态渲染，服务器压力大，访问速度慢（尤其是国内访问海外服务器）
- 安全隐患多，WordPress 是黑客最爱攻击的目标之一，需要定期更新和维护
- 一旦服务器出问题，网站直接挂掉

**我的判断：** 如果你只是个人博客，WordPress 的维护成本远大于收益。

---

### Hexo / Jekyll

**适合谁：** 有一定技术基础，想要静态博客但不排斥 Node.js / Ruby 环境的用户。

**优点：** 主题丰富，社区成熟，教程多。

**缺点：**
- **Hexo** 依赖 Node.js 和大量 npm 包，本地环境搭建麻烦，npm 依赖冲突是家常便饭
- **Jekyll** 依赖 Ruby 环境，Windows 上安装配置复杂
- 随着文章增多，本地构建速度越来越慢（几百篇文章可能要等十几秒）

---

### Notion + NotionNext（我踩过的坑）

**适合谁：** 重度 Notion 用户，想把 Notion 当 CMS 用的人。

**优点：** Notion 写作体验好，数据库功能强大。

**缺点：**
- 高度依赖 NotionNext 框架的稳定性，框架报错直接影响网站
- 基于 Next.js，深度自定义需要学习 React 生态
- 依赖 Notion API，存在速率限制和接口变动风险
- 内容存在 Notion 平台，不完全由自己掌控

---

### Astro / Gatsby

**适合谁：** 前端开发者，需要构建复杂交互式网页的用户。

**优点：** 组件化能力强，支持 React/Vue/Svelte，能构建非常复杂的 Web 应用。

**缺点：**
- 学习曲线陡，对非前端开发者不友好
- 配置复杂，维护成本高
- 如果你只是想写博客，用这些框架就像"用大炮打蚊子"

---

### Hugo ✅

**适合谁：** 想专注写内容、追求网站稳定、希望能自由定制但不想学复杂 JS 框架的用户。

**核心优势：**

**① 零依赖，一个文件搞定**

Hugo 是用 Go 语言编译的单一二进制文件，下载后直接用，不需要安装 Node.js、Ruby、Python 或任何运行时环境。Windows 上双击就能跑，不存在"依赖冲突"的问题。

**② 构建速度极快**

Hugo 是目前公认最快的静态网站生成器。数千篇文章，构建时间通常在 1 秒以内。本地预览时修改文章，页面几乎实时刷新，写作体验非常流畅。

**③ 模板语言简单，自定义门槛低**

Hugo 使用自己的 Go Template 语法，不需要了解 React、Vue 或任何 JS 框架。想改个样式、加个功能，直接改 HTML 模板和 CSS 就行，所见即所得。

**④ 内容完全由自己掌控**

所有文章都是本地的 Markdown 文件，存在你自己的电脑和 GitHub 仓库里。没有第三方平台的依赖，没有 API 限速，内容迁移也极其简单。

**⑤ 部署稳定，几乎不需要维护**

配合 Cloudflare Pages 部署，静态文件全球 CDN 分发，没有服务器需要维护，也没有数据库需要备份。框架本身的更新不影响已部署的网站，不会出现"更新后网站挂了"的情况。

## 1.4 Hugo v0.158 的主要新特性（2026 年 3 月）
> 这里注意：v0.158是制作此文档时使用的版本，其中带来了几个值得关注的改进。源于Hugo官方社区活跃，版本也在持久更新，版本号也会随之变化。
>

**更快的编译速度**
底层模板渲染引擎进一步优化，对复杂模板和大量页面的处理效率有显著提升。

**更强的原生图片处理**
支持更多现代图片格式（AVIF / WebP）的原生无损压缩和缩放，不需要额外安装图片处理工具，Hugo 直接搞定。

**增强的多语言支持**
i18n 配置逻辑大幅简化，如果你有计划做中英双语博客，v0.158 让这件事变得简单很多。

**css.Build 极速构建**
SCSS 样式文件的编译速度大幅提升，这对使用 Stack 主题这类依赖 SCSS 的模板来说体验改善明显。

## 1.5 我现在的工作流

换到 Hugo 之后，我日常写博客的流程变成了这样：

```
1. 在本地用 VS Code 写 Markdown 文章
2. hugo server 实时预览效果
3. 写完后 git push 推送到 GitHub
4. Cloudflare Pages 自动构建，约 1 分钟全球上线
```

整个过程没有任何平台依赖，没有神秘报错，网站从来没有因为框架问题挂掉过。

这才是我想要的状态。
